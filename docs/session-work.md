# Work in an existing coding-agent session

`baton work` runs a configured Baton pipeline in an existing Git worktree without a server. A coding-agent TUI can use the CLI as an interface; Pi has a dedicated extension. The CLI executes configured agents through Baton adapters and the configured runtime. Baton does not allocate or remove this worktree.

Work and server runs use shared pipeline models and runtime adapters but have separate records, composition and workspace ownership. Work sessions are not shown in the server Runs UI.

## Install and configure

For Pi, install an official Baton release and Pi, then run `baton install pi` and restart or reload Pi. The command downloads the UI extension from the CLI's matching release tag into `~/.pi/agent/extensions/baton.ts`, replacing an existing Baton extension without changing other extensions; repeat after upgrading Baton. For a development build, use the local extension directly. Use `/baton` to enter a task and start a run, `/baton RUN_ID` or `/baton resume RUN_ID` to resume, `/baton list [PAGE]` to page through local work sessions, `/baton inspect RUN_ID` to inspect a persisted work record, and `/baton help` for syntax and side effects. List and inspect are read-only; resume can execute configured steps. At human pauses, the extension prominently shows the waiting step, available decisions, and how to continue or resume later before displaying the prior handoff. Long handoffs are shown in 7,000-character chunks on demand (each below the 8,000-character message budget) rather than flooded or discarded; the extension asks for an explicit selection, response, and confirmation. Lists and details have distinct headings. Running updates show a RUNNING state, step, and attempt in both the message and status line; results and terminal states use labeled messages, and failures are presented as Baton errors. It invokes the CLI; it does not start Pi subagents.

The Pi extension shows the current step and completed results, not live Rig tool activity or Pi subagent activity. It invokes `baton work execute`, which executes the configured Baton step; it does not capture the surrounding Pi session or launch Pi subagents. Listed runs are local `baton work` sessions stored in `.baton/work/`, not server runs shown in the Runs UI. List pages contain at most 50 sessions and adapt to an output-size budget; long displayed fields are shortened with an omission marker, and previous/next commands retain access to every session. Inspect shows at most 30 recent steps and marks omitted earlier steps. Step output/error text and total display output are bounded, and inspect excludes task text, configuration snapshots, and runtime trace metadata. The extension does not stream live execution activity. It stops on a CLI error; inspect the run before retrying. To cancel a running step, invoke `baton work cancel --run RUN_ID` from another terminal.

To test the local checkout, run `mise run dev-pi` from the repository root. It builds the CLI and starts Pi with the local Baton extension; other Pi extensions are disabled for that session.

Other coding-agent TUIs, such as Claude Code and Codex, can invoke the CLI directly. They do not yet have a dedicated Baton UI integration.

Configure agents in `.baton/agents/` and pipelines in `.baton/pipelines/`. Rig agents use their configured provider, model, tool permissions and credential ID; credentials must exist in Baton's local credential vault. Assigned project skills and project instructions are provided by the runtime. Agent skills and tools are not a security boundary: commands run with local user permissions and a worktree is not a sandbox.

Baton stores the task text literally and does not fetch issue URLs. Resolve an issue and include its requirements and acceptance criteria in the task text before starting.

## CLI

Run commands in an existing Git worktree, or supply `--workspace PATH`:

```sh
baton work start --issue 'Task and acceptance criteria' --pipeline factory
baton work pipelines
baton work status
baton work next --run RUN_ID
baton work execute --run RUN_ID
baton work respond --run RUN_ID --result human-response.json
baton work cancel --run RUN_ID
```

`baton work pipelines` lists configured pipeline IDs as JSON for interactive integrations such as Pi. If only one pipeline exists, `--pipeline` may be omitted. Start creates a new run; use its ID to resume. `next` returns the current step, attempt, revision, allowed outcomes, checks and latest handoff without replaying the full trace. `execute` runs one agent or shell step and submits its result through Baton. Repeat until completion, an error, or a human pause. Outputs are JSON; errors are JSON on stderr with a nonzero exit code. `status --run ID` returns the persisted run.

Human steps require an explicit user decision via `respond`. Supply a JSON file containing the current `revision`, `stepId`, `attempt`, `outcome`, and `response`. This is a protocol distinction, not identity authentication: a process with shell access can invoke `respond`.

`submit` remains available for explicit structured submissions. A result contains `revision`, `stepId`, `attempt`, `outcome`, and a nonempty `summary`. Stale or invalid results are rejected. Integrations must not fabricate a result or human decision.

For routed agent steps, the configured runtime must report one of that step's configured outcomes. Baton does not accept `progress` or automatically repeat a step. Explicit workflow loops count toward the Work attempt limit, which defaults to 50 attempts including human steps and can be configured from 1 to 1000 via `--max-attempts`. For Rig and Pi, a missing or invalid agent outcome triggers up to two follow-up requests in the same session; if neither yields a valid outcome, the run fails without repeating the task. Historical runs containing `progress` remain readable, but unfinished runs no longer accept it.

Rig persists each agent's conversation under `runtime-sessions/<run-id>/agent-<agent-id>/` in the project's local credential-vault directory, outside the workspace. Subsequent attempts of the same agent in that run restore its conversation and receive the latest handoff and, when `includeTask: true`, the original task; different agents and new runs do not share conversations. The setting cannot remove information already present in a restored conversation. These files can contain conversation and tool output; keep secrets out of them and out of version control. Conversation files are not a redacted, bounded, or retention-managed audit log: they may contain sensitive data, are not automatically deleted, and should be protected and removed by the operator when no longer needed. Persisted Runs traces contain bounded structural metadata: model-request message roles and available tool names, model response status, and tool call/result names and status. They do not contain prompts, conversation transcripts, tool arguments or result contents, provider usage, or cost estimates. Request/wire metadata capture is limited to 128 entries and 64 KiB per capture; each record is at most 4 KiB. Run trace storage is limited to 512 entries, 8 KiB per entry, and 256 KiB of recorded content/metadata per run; oversized entries are marked truncated; when an entry or run limit is reached, later trace activity is omitted and a `traceTruncated` marker is stored. These limits bound new trace data, not older run files or the separate Rig conversation store. Managed Rig and CLI Work executions persist the restricted request metadata and last-observed event as the runtime reports it; the Runs UI refreshes live, and `baton work status --run RUN_ID` can inspect a Work record while execution continues. No model prose, tool arguments, tool result contents, or shell activity is captured, and the Pi command itself waits for `baton work execute` rather than relaying live activity or capturing the surrounding Pi session. Treat saved Rig conversation files separately from the restricted Runs trace. Provider token usage and cost are not currently reported; missing data is unavailable, not zero. Model/provider identity is shown from the configured agent when present. Sessions from the former workspace-wide layout are not automatically imported, because their run ownership cannot be verified.

Pi persists each agent's conversation in `runtime-sessions/<run-id>/agent-<agent-id>/pi/` in the same local vault. Subsequent invocations in the same run resume it and still receive the newly selected handoff and recovery instructions; earlier conversation remains visible regardless of context selection. Different agents and runs do not share sessions. Pi session files can contain sensitive conversation and tool output and are not automatically deleted. If an expected session is missing, invalid or larger than 16 MiB, Baton fails instead of silently starting over. An interrupted or failed invocation leaves a `baton-inflight` marker: inspect and reconcile side effects before manually removing it. Fake runtimes do not support resumption and repeated invocations fail explicitly.

Rig's compaction plugin manages model context near the provider's window. Before starting a turn, Baton additionally rejects a restored conversation larger than 4 MiB of serialized JSON; reconcile the workspace and start a new run if this limit is reached. Baton does not silently replace a missing or unreadable expected session with empty history.

## Checks and workspace ownership

Add explicit process gates at start, for example `--check 'build=cargo test'`. Baton runs applicable checks in the worktree before accepting successful outcomes. Failed checks reject the submission; successful results are persisted separately from agent summaries. Checks time out after 300 seconds and their recorded output is bounded. Do not include secrets in task text, checks or summaries.

Work records are stored under `.baton/work/`, independently of server records. The workspace remains externally owned; completion or cancellation never removes it. Configuration is snapshotted at start. Concurrent changes to the same workspace remain the user's responsibility.

While an agent or command runs, status and cancellation commands may run concurrently. Only one Work execution can use the workspace at a time. Cancellation is cooperative and does not undo changes already made. A failed or interrupted Rig execution leaves `baton-inflight` in its agent session directory and cannot be retried automatically. Inspect the run, session and workspace and reconcile possible side effects (including commits and network actions) before manually removing that marker and retrying. If the expected session is missing, corrupt or repaired during restoration, stop and reconcile rather than assuming the prior context survived. In server mode an interrupted in-flight execution fails on restart instead of replaying automatically; after reconciliation, start a new run. There are no automatic commits, merges or issue updates.
