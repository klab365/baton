# Tasks

Tasks are runtime data stored as individual JSON files in `.baton/tasks/`, not in the versioned `.baton/config.json`. Keep this directory out of version control: new projects ignore it automatically; existing projects should add `tasks/` to `.baton/.gitignore`. Task files contain user prompts and should be treated as private local data.

The API exposes `GET /api/tasks`, `POST /api/tasks`, and `GET`, `PUT`, `DELETE /api/tasks/{id}`. POST and PUT accept `title`, `description`, `acceptanceCriteria`, and `pipelineId`. The title and description must be nonblank; acceptance criteria are optional. The selected pipeline must exist in the current valid project configuration. Missing tasks return 404; invalid selections return 400. PUT replaces the editable fields. Status and timestamps are server-owned.

Tasks begin in `draft`; saving never starts execution. A task stores its text, pipeline ID and (after first start) its owned worktree, not a project-configuration snapshot. Sequential runs for that task reuse the same worktree; different tasks get independent worktrees and may run concurrently. Starting a run uses the current project configuration and saves an immutable snapshot on that run. Thus configuration changes affect future runs, while existing runs remain reproducible. Pipelines may include a configured commit agent after review and before human approval; that agent can commit task changes directly on the task branch. Baton itself does not create commits. The task worktree is force-removed when the task is marked `done` or deleted; this discards uncommitted changes and task-local Rig session data. Task deletion requires UI confirmation. Updating a task requires selecting a currently valid pipeline. Older task files may contain a legacy `configSnapshot`; it is ignored when loaded and omitted on the next save. Timestamps are UTC RFC 3339 strings with millisecond precision (for example, `2025-01-02T03:04:05.678Z`).

Writes use a synced temporary file and atomic rename. The backend serializes task operations within its process. Run one backend per project directory; concurrent independent backend processes are not supported. No execution-target resources or run-start endpoints are introduced.
